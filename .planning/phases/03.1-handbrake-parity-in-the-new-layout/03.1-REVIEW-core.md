# Phase 03.1: Code Review Report (HyperVideoCore)

**Reviewed:** 2026-10-23T04:17:59Z
**Depth:** standard (diff 711f915..HEAD, plus the callers and callees of each changed function)
**Files Reviewed:** 54
**Status:** issues_found

## Summary

I reviewed the whole HyperVideoCore diff for this phase: the audio, subtitle, chapter and video pump split, the planners, AudioGain, the peak limiter, A/V alignment, crop detection, geometry/anamorphic/padding, the new filters, WriterMetadata, the MKV metadata and track flags, the model types with their lenient decoding, and the HandBrake preset mapping.

The D-05 defaults hold up. `frameRateMode = .constant`, `speed = .balanced`, `profile/level = .auto`, `sampleRate = .hz48000`, `cropMode = .custom` with a zero crop, `anamorphic = .none`, padding none, `markers = nil` (follows keepMetadata), `automaticNaming = false`, `alignAVStart = false` and empty languages and track lists together give the same reader/writer dictionaries and track selection as 711f915. The AAC bitrate clamp gives the old values at 48 kHz. Every new field decodes with `decodeIfPresent`, and legacy `prioritizeSpeed` maps correctly. One exception: the MKV metadata change emits new tags with default settings (WR-06).

I checked two problems empirically with throwaway Swift probes:
1. `AVAssetWriterInputGroup(inputs:defaultInput:)` raises `NSInvalidArgumentException` when `defaultInput` is not one of `inputs` (CR-01).
2. A track written with only `languageCode` reads back with `extendedLanguageTag == nil` (CR-02). In the same probe, `Locale.Language(identifier: "fre"/"ger"/"chi")` returns no alpha-3 code (WR-01).

## Critical Issues

### CR-01: A closed-caption track marked Default crashes the encode (NSInvalidArgumentException)

**File:** `Sources/HyperVideoCore/Engine/PipelineFactory+Subtitles.swift:17-30` (with `PipelineFactory.swift:37-42`)
**Issue:** `subtitlePumps` sets `defaultInput = pump.input` for any planned entry with `isDefault`, and that includes closed-caption tracks (`kind == .closedCaption`, which MOV keeps). The UI shows the Default radio for CC rows too (`SubtitleTrackRow.swift:42`). The group is then built only from `.subtitle` inputs: `groupAlternates(pumps.map(\.input).filter { $0.mediaType == .subtitle }, defaultInput: defaultInput)`. So the default input is not in `inputs`. With two or more subtitle inputs (two tx3g tracks, or one tx3g track plus an external SRT), `AVAssetWriterInputGroup(inputs:defaultInput:)` throws `*** -[AVAssetWriterInputGroup initWithInputs:defaultInput:] invalid parameter not satisfying: defaultInput == nil || [inputs containsObject:defaultInput]`. I reproduced this in a probe. It is an uncaught Objective-C exception, so the app terminates. Before it throws, every subtitle track has also been marked disabled.
**Fix:** Only accept a default that is in the group. Also stop offering Default for CC tracks, or don't plan it:
```swift
let subtitleInputs = pumps.map(\.input).filter { $0.mediaType == .subtitle }
let groupDefault = defaultInput.flatMap { d in subtitleInputs.contains { $0 === d } ? d : nil }
groupAlternates(subtitleInputs, defaultInput: groupDefault)
```
Also harden `groupAlternates` itself: `guard defaultInput.map({ d in inputs.contains { $0 === d } }) ?? true else { return }`. In `SubtitleTrackPlanner.explicitEntries`, set `isDefault` only when `source.kind == .subtitle`.

### CR-02: The audio language filter never matches typical MP4/MOV sources (uses `extendedLanguageTag` only)

**File:** `Sources/HyperVideoCore/Engine/PipelineFactory+Audio.swift:7-9` (also `:21`, `:37`)
**Issue:** `AudioSourceTrack.language` comes only from `track.load(.extendedLanguageTag)`. Files muxed by HandBrake, ffmpeg and most tools carry only the `mdhd` ISO 639-2 code, and for those AVFoundation returns `extendedLanguageTag == nil` (probe: `ext=nil code=fra`). As a result `LanguageFilter.matches(nil, in: ["fra"])` is always false, `behaviourPlan` falls back to `[firstSource]`, and the new AUD language selection (and imported `AudioLanguageList`) silently does nothing on most real files. The subtitle path already does `language ?? code`. A related, older problem: the audio writer input only gets `extendedLanguageTag = language`, never `languageCode`, so those same files come out with audio tagged "und".
**Fix:**
```swift
let (tag, code) = try await track.load(.extendedLanguageTag, .languageCode)
sources.append(AudioSourceTrack(id: Int(track.trackID), language: tag ?? code))
// in audioPump:
let (formats, language, code) = try await track.load(.formatDescriptions, .extendedLanguageTag, .languageCode)
input.extendedLanguageTag = language
input.languageCode = code
```
Add an integration test with a source whose audio has only `languageCode` set.

## Warnings

### WR-01: HandBrake ISO 639-2/B codes (fre, ger, chi, cze, dut, gre, …) never match

**File:** `Sources/HyperVideoCore/Models/LanguageFilter.swift:9`
**Issue:** `normalized` relies on `Locale.Language(identifier:).languageCode?.identifier(.alpha3)`. That returns `nil` for the bibliographic codes HandBrake writes in `AudioLanguageList`/`SubtitleLanguageList` ("fre", "ger", "chi"; confirmed in a probe), so they fall through unchanged. Track languages come from AVFoundation as BCP-47 or terminology codes ("fr" → "fra", "fra"). So an imported preset asking for French or German audio/subtitles matches nothing: audio falls back to the first track, and subtitles are all dropped.
**Fix:** Before the Locale lookup, map ISO 639-2/B to /T with a small table: `["fre":"fra","ger":"deu","chi":"zho","cze":"ces","dut":"nld","gre":"ell","per":"fas","rum":"ron","slo":"slk","wel":"cym","alb":"sqi","arm":"hye","baq":"eus","bur":"mya","geo":"kat","ice":"isl","mac":"mkd","mao":"mri","may":"msa","tib":"bod"]`. Add a test with `matches("fr", in: ["fre"])`.

### WR-02: HandBrake `copy:<codec>` becomes an unconditional passthrough

**File:** `Sources/HyperVideoCore/Models/HandBrakePresets+Audio.swift:53`
**Issue:** In HandBrake, `copy:ac3` means "copy only if the source is AC-3, otherwise use the fallback encoder". Here it maps to `.passthrough`, which copies any codec. If the source is PCM, ALAC or another codec the container can't hold, `attach` throws `cannotConfigure` and the whole job fails. If the source is a different compressed codec, it is copied even though the preset restricts it.
**Fix:** Map `copy:X` to `.autoPassthru`. Because `allowedPassthru` is preset-wide, it can't be narrowed to `[X]` for just this entry, so give `AudioEncoding` an optional per-encoding allow set, or fall back to the import note if that isn't possible. That way the AutoPassthru container check and the fallback both apply.

### WR-03: Explicit per-track lists override "No Audio" / "None" and the estimates

**File:** `Sources/HyperVideoCore/Engine/AudioTrackPlanner.swift:17-21`, `Sources/HyperVideoCore/Engine/SubtitleTrackPlanner.swift:31-35`, `Sources/HyperVideoCore/Models/Estimates.swift:72-84`
**Issue:**
- When `audioOptions.tracks` is non-empty, `plan` ignores `audioCodec == .none` and `audioTracks == .none`. A video that has a per-track list still gets audio after the user picks "No Audio" in the apply-to-all inspector. The same happens for subtitles with `subtitles == .none`.
- `OutputEstimate.audioBitsPerSecond` and `fallbackAudioBitsPerSecond` use `settings.audioEncodings` and `audioTracks` only. They ignore the explicit list, the language filter and `extraFirstTrackOnly`, so the size prediction is wrong whenever those are used.

**Fix:** In `plan`, return `[]` when `settings.audioCodec == .none || settings.audioTracks == .none`, or have the inspector clear `tracks` when it sets "No Audio". Do the same with `subtitles == .none`. Base the estimates on `AudioTrackPlanner.plan(sources: info.audioTracks.map { AudioSourceTrack(id: $0.id, language: $0.language) }, settings:)`.

### WR-04: Filtered path renders anamorphic sources at storage width inside a display-width frame

**File:** `Sources/HyperVideoCore/Engine/FrameFilter.swift:23-27`, `Sources/HyperVideoCore/Engine/PipelineFactory+Video.swift:142-144`
**Issue:** The plan's transform is built in `naturalSize` space. For PAR-tagged tracks that is the display size (confirmed by `naturalSizeOfTaggedClipIsDisplaySize`, 640×360 for a 480×360 4:3-PAR clip). `FilterCompositor` passes `CIImage(cvPixelBuffer: source)`, which has the storage extent (480 wide), with no horizontal scale. Whenever `filtered` is true, the picture comes out about 25% narrower with a canvas-coloured strip on the right. `filtered` is true for deinterlace (auto, on interlaced sources such as DV, which is typically PAR-tagged), denoise, chroma smooth, sharpen, grayscale or burn-in. The bug predates this phase, but the phase adds four new filters that reach it, plus the anamorphic option. The anamorphic test only covers the plain compositor path.
**Fix:** Normalise the frame to `sourceSize` before filtering:
```swift
let extent = image.extent
var frame = image.transformed(by: CGAffineTransform(scaleX: sourceSize.width / extent.width,
                                                     y: sourceSize.height / extent.height))
```
Add a test: a PAR clip with `filters.grayscale = true`, then check that the output picture fills the frame (sample the right edge).

### WR-05: AudioGain assumes interleaved Float32 and silently drops the gain on failure

**File:** `Sources/HyperVideoCore/Engine/AudioGain.swift:17-31, 58`
**Issue:** `apply` reinterprets the raw block buffer as `[Float]` without checking the buffer's ASBD. It is correct only while `audioReaderPCM` stays 32-bit float, interleaved and little-endian, a coupling that nothing enforces. Any failure (`CMBlockBufferCopyDataBytes`, buffer creation) returns `nil`, and `transform` then substitutes the un-gained buffer. The output ends up with gain on some packets and none on others, and nothing is reported.
**Fix:** Guard on the format, and fail loudly instead of passing audio through:
```swift
guard let asbd = CMAudioFormatDescriptionGetStreamBasicDescription(format)?.pointee,
      asbd.mFormatID == kAudioFormatLinearPCM, asbd.mFormatFlags & kAudioFormatFlagIsFloat != 0,
      asbd.mBitsPerChannel == 32, asbd.mFormatFlags & kAudioFormatFlagIsNonInterleaved == 0 else { return nil }
```
In `transform`, return `apply(...)` (nil drops the sample) or set the cancel flag, so a failure isn't silent partial gain. Also check that `count == sampleCount * channels`.

### WR-06: MKV output gains an ACTOR (and iTunes DATE_RELEASED) tag with default settings (D-05)

**File:** `Sources/HyperVideoCore/Engine/Matroska/MatroskaMetadata.swift:19-21`
**Issue:** `ACTOR` is read from `.quickTimeMetadataArtist` / `.iTunesMetadataArtist`. Those are the same items that feed `ARTIST` through `commonIdentifierArtist`. Any source with an artist tag converted to MKV with `keepMetadata = true` (the default) now gets a duplicate `ACTOR` tag. It also gains `DATE_RELEASED` from iTunes `©day`. Old queues therefore no longer produce identical MKV files, which breaks D-05. The duplication also mislabels music-video artists as actors.
**Fix:** Emit `ACTOR` only when the value came from `settings.tags.actors`, for example by passing `MetadataTags` into `MatroskaMetadata.metadata`. Otherwise drop `ACTOR` and keep `ARTIST`, as before.

### WR-07: Align A/V Start only works when the source has a leading empty edit

**File:** `Sources/HyperVideoCore/Engine/AVAlignment.swift:20-23`
**Issue:** `firstFrameTime` takes `segments.first { !$0.isEmpty }?.timeMapping.target.start`. The most common A/V offset has no edit list: the first video sample PTS sits after zero (B-frame CTS offset, or remuxed TS/MP4 with a start offset). There the only segment starts at 0, so the option does nothing. The test passes only because `StressClip` is written by AVAssetWriter, which creates an empty edit.
**Fix:** Also read the first video sample's presentation time, for example with a short-lived `AVAssetReaderTrackOutput(outputSettings: nil)` limited to the first second, or `AVSampleCursor` on macOS 15. Map it through the segment's time mapping, and use the later of that and the edit start.

### WR-08: "Forced only" drops whole tracks instead of keeping forced cues, and `SubtitlePlanEntry.forced` is never used

**File:** `Sources/HyperVideoCore/Engine/SubtitleTrackPlanner.swift:52-58`, `Sources/HyperVideoCore/Engine/PipelineFactory+Subtitles.swift:17-24`
**Issue:**
- `!setting.forcedOnly || source.forcedOnly` excludes every track that isn't flagged as entirely forced. So ticking "Forced only" on an ordinary track (HandBrake's meaning is "keep only the forced lines") removes the track completely, and the user isn't told.
- `entry.forced` is computed but never read. The copied track is never flagged forced, unlike external files, which get `kCMTextDisplayFlag_allSubtitlesForced`.

**Fix:** Either implement the HandBrake semantics, or disable the toggle unless `SubtitleTrackInfo.isForcedOnly`. When it applies, mark the output forced, for example by using `entry.forced` to choose a forced-flagged format hint, or by adding the `.containsOnlyForcedSubtitles` characteristic through the input's `mediaCharacteristics` metadata. Otherwise remove the dead `forced` field.

## Info

### IN-01: Force unwraps violate D-09

**File:** `Sources/HyperVideoCore/Engine/AudioGain.swift:26, 44`, `Sources/HyperVideoCore/Engine/TimedText.swift:49`
**Issue:** `$0.baseAddress!`. It is safe today because `count > 0` is guarded, but the phase rules say "no force unwraps".
**Fix:** Use `guard let base = $0.baseAddress else { return kCMBlockBufferBadPointerParameterErr }`.

### IN-02: Function-size rule (<50 lines) exceeded

**File:** `Sources/HyperVideoCore/Engine/PipelineFactory+Video.swift:39-89` (51 lines), `Sources/HyperVideoCore/Engine/TranscodeEngine.swift:73-184` (112 lines; this phase added lines to it)
**Fix:** In `videoPump`, extract the passthrough branch and the composition-plan construction. Split `transcode` into setup, `runPumps` and finalize helpers.

### IN-03: `PeakGate` is needlessly `@unchecked Sendable`

**File:** `Sources/HyperVideoCore/Engine/PipelineFactory+Video.swift:19`
**Issue:** The class's only state is a `Mutex<PeakRateLimiter>`, which is already Sendable. `@unchecked` only turns off compiler checking.
**Fix:** Declare it `final class PeakGate: Sendable`.

### IN-04: The peak limiter gives well under the peak for some source rates

**File:** `Sources/HyperVideoCore/Engine/PeakRateLimiter.swift:12-16`
**Issue:** It admits greedily from the last kept frame. A 50 fps source with peak 30 comes out at 25 fps, and a 120 fps source with peak 50 at 40 fps. HandBrake would keep close to the peak.
**Fix:** Track an ideal grid instead (`nextSlot += minimumInterval`) and admit the first frame at or after each slot.

### IN-05: `ChapterCSV.format` doesn't round-trip titles that contain newlines

**File:** `Sources/HyperVideoCore/Models/ChapterCSV.swift:36-40`
**Issue:** A title containing `\n` produces a line that `parse` then rejects with `invalidLine`.
**Fix:** Replace newlines with spaces when formatting. Also cap the title length that reaches `TimedText.sample`: its `prefix(UInt16.max)` byte cut can split a UTF-8 scalar.

### IN-06: The 7.1 layout uses MPEG_7_1_B (front-centre pair), not a rear-surround 7.1

**File:** `Sources/HyperVideoCore/Engine/OutputSettingsBuilder+Audio.swift:72`
**Issue:** HandBrake's 7.1 mixdown is L R C LFE Ls Rs Lrs Rrs. `MPEG_7_1_B` places the extra pair as Lc/Rc (front), so the reader's downmix routes Blu-ray back-surrounds to the front.
**Fix:** Use `kAudioChannelLayoutTag_AAC_7_1_B` / `MPEG_7_1_C` for 8 channels and test that `canApply` accepts it.

### IN-07: H.264 Baseline is sent with frame reordering allowed; Auto Passthru estimates ignore the fallback

**File:** `Sources/HyperVideoCore/Engine/OutputSettingsBuilder.swift:101-108`, `Sources/HyperVideoCore/Models/Estimates.swift:93`
**Issue:**
- An imported Baseline preset keeps `allowBFrames = true`. Baseline has no B-frames, so this depends on VideoToolbox quietly ignoring it.
- `.autoPassthru` is estimated as a full copy even when the fallback encoder will be used.

**Fix:** Force `AVVideoAllowFrameReorderingKey = false` when the resolved profile is `.baseline`. For estimation, treat `.autoPassthru` as a copy only when `AutoPassthru.copies` would be true for that track's codec.
